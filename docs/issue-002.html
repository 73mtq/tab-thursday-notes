第一部分 · Agent 的工作形态：从会话到任务

01 海涛：Comma 开源 AI 助理

相关链接主页 · haitao.wikiComma源码

身份：Tab 星期四联合发起人之一，haitao.wiki。第一期分享的是 iPhone Use Pro（用 AirPlay + 蓝牙 HID 操控真机），本期方向从「让 Agent 操作设备」转向「让 Agent 组织工作」。 分享对象：comma.surf 与 github.com/AFK-surf/Comma。 关键词：任务调度、并行 Agent、云端电脑、待审核队列、自托管。

他讲了什么

Comma 是一个开源 AI 助理，用户只面对一个对话框。调度层把每个请求拆成独立任务，交给并行运行的 Agent，这些 Agent 在云端电脑上操作邮件、Linear、Notion 和 GitHub；需要用户决定的事项进入待审核队列。项目可以自托管，也可以通过 Telegram 和 Signal 下达任务。

海涛给出的判断是：按任务而非按会话组织工作，是继 Claude Code、Codex 和话题式协作平台之后的下一种 Agent 形态。

公开页面补充（comma.surf 与 GitHub 仓库，2026-11-09 可访问）：官网的定义是 "a free, open source personal AI agent"，并强调 "always on, proactive and sessionless"、"Comma is built around Tasks, not chats."。架构原文为 "You talk to one Router, and it hands each Task to a Worker. Choose a model for each role, or let Codex or Claude Code be the Worker." ——即 Router 只做承接与分派，Worker 才是执行者，且两者可以分别选模型。看板三列是 In progress / Needs Review / Done，官网写明 "When a decision is yours, the Task waits for you in Needs Review."，另有一句权限边界："Your computers stay read-only until you allow more."。Routines 示例覆盖 Gmail、Linear、Notion、GitHub、Slack、Google Drive、Google Meet。技术栈为 Go / Elixir / Lean，客户端是 Web + Electron + React，服务端为 Elixir umbrella（Salix、Comma product、Bridge For Teams），仓库内还带 tla/ 形式化模型。许可证 AGPL-3.0-only，自托管不收费，免费版需自带模型 key。

需要说明：汇总页的「并行运行的 Agent」「一个对话框 + 调度层」并非官网逐字表述，官网写的是 Router → Worker 与 Task 拆分；汇总页的「邮件」在官网具体为 Gmail。本文后续按官网术语叙述，差异处保留汇总页原话作为对照。

关键点拆解

第一，改变的是组织单位，不是模型能力。 会话是时间轴上的连续容器，任务是目标导向的离散单元。会话隐含单线程、上下文持续累积、一个用户对应一个 Agent；任务隐含可并行、可独立验收、可失败重试。Claude Code 与 Codex 是「一个会话里推进一个任务」，话题式协作平台是「多个 Agent 共享一个上下文讨论」，Comma 是「一个入口拆成 N 个彼此隔离的任务」。这三代的差别不在推理质量，而在调度拓扑与上下文是否共享：从独享、到共享、到隔离。

第二，并行 Agent 的门槛是状态冲突，不是并发数。 邮件、Linear、Notion、GitHub 四个系统描述的是同一个现实：一个 issue 往往同时对应一封邮件、一条 Notion 记录和一次代码提交。两个 Agent 同时改，谁赢？这类系统必须回答幂等、加锁、冲突合并或事件溯源。汇总页未展开这部分，但它是架构上的必答题，也是「看起来只是多加几个 Agent」最容易翻车的地方。【分析，非汇总页原文】

第三，待审核队列把人的注意力当作一种需要调度的资源。 它没有让 Agent 随时打断人，也没有要求人一直盯着 Agent，而是把「需要人决策」累积成一个可批量处理的队列。这与第一期 Edward Luo 的 Vibe Island 是同一个问题的两种解法：Vibe Island 把审批放进刘海，做实时中断管理；Comma 把审批放进队列，做异步批处理。前者适合任务少、决策急，后者适合任务多、决策可延迟。两期连起来看，能看出这批人已经把「何时打断人」当作一个独立的设计维度。

第四，云端电脑是能力边界与信任边界的一次交换。 Agent 在远端独立环境操作，不占用户本机、不要求本机在线、不碰本地浏览器的登录态，代价是凭据与会话要托管到云端。「可自托管」正是对这个代价的回应。这与第一期 Gloria X 的 Ego Lite 构成一组对照：Ego Lite 把 Agent 关进本机 Space、复用用户自己的登录态；Comma 把整个工作环境搬上云。一个强调数据不出本机，一个强调人不必在场，取舍不同，但都在回答「Agent 该在哪里活」。

第五，Telegram / Signal 作为入口，隐含一个关于任务粒度的假设。 消息 App 适合下达粗粒度、无需实时观察过程的任务；如果任务需要边看边改，手机上就没法用。所以这不是「多端适配」的小功能，而是产品对任务粒度的一次表态：任务必须完整到可以用一句话交代、并能在没有监督的情况下跑完。

第六，「下一种 Agent 形态」是分享者的判断，不是已验证的行业结论。 汇总页没有给出任务成功率、并行加速比或与其他形态的对比数据。它的价值在于提供了一个清晰的设计坐标（以任务为单位），而非证明该坐标更优。

第七，海涛在同一期的线上分享里贴出的文章，其实是这次分享的理论注脚。 他推荐了 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》（2026-10-23）。该文给出的架构正是双层 Router + Worker：Router 负责理解意图、拆任务、分派与汇总，Worker 负责单一任务的完整执行并可自主规划步骤；文章明确写「Session 应当是系统的实现细节，而不应是用户的认知负担」，并给出两个很有分量的观察：「一个人通常只能同时跟进 3 到 5 个活跃 Session」、「单任务的上限取决于模型能力，多任务的上限取决于人的注意力」。

这与 Comma 的 "sessionless"、"Tasks, not chats"、Needs Review 看板几乎逐条对应：Router/Worker 双层解决任务拆分，看板解决「人的注意力」这个真实瓶颈，待审核队列解决 3–5 个并发的认知上限。文章还提到用 skill 把领域经验注入 Worker、用 skill_search 动态加载、以及子任务携带压缩上下文向下传递——与本期 Hao 的 skill 化、Sean Shao 的全局提示词同属一套工程语言。换句话说，海涛不是随手贴了一篇相关文章，而是给自己分享的产品给出了同一时期、另一支团队独立得出的架构论证。 这是本期最值得留意的一处内部呼应。

可迁移的方法

  1. 设计 Agent 系统时先定「组织单位」——会话、任务还是话题，再选模型与框架。
  2. 把需要人决策的事项做成异步队列，而不是实时弹窗，让审批带宽可被批量使用。
  3. 提升并行度之前，先定义跨系统状态冲突的处理规则。
  4. 入口形态要与任务粒度匹配：消息入口对应「交代完就能走」的任务。

边界与提醒

云端电脑集中持有邮件、代码、项目管理等多个系统的凭据，是高价值攻击目标；自托管并未消除风险，只是把风险与运维责任一起转回用户。官网对自托管的要求并不轻：需要 Docker Compose v2.24+、模型服务商账号、Cloudflare 配置与真实 SMTP，服务端同时涉及 Go、Elixir、Lean 三套运行时，还要求配合特定模型组合——这已经不是「跑个容器」的门槛。AGPL-3.0-only 也意味着若对外提供网络服务，衍生代码需按许可证开放。

待审核队列会积压——并行 Agent 的产出速度常常超过人能消化的速度，此时瓶颈从执行转成审批，恰是 DeepSeek Harness 文章所说「多任务的上限取决于人的注意力」。更前置的风险在调度层本身：判断错了任务之间的依赖，并行只会把错误放大得更快。此外，与第一期的 iPhone Use Pro 类似，这类方案高度依赖上游服务接口的稳定性，Gmail、Linear、Notion、GitHub 任一侧改版都可能影响可用性；官网示例里 "Signups rose 12% to 1,590" 属于演示数据，不是效果证明。

身份：github.com/Peterleixx，分享中明确说明自己没有算法背景，实验在一台 MacBook 上完成。 分享对象：一次「让 AI Agent 自主研究」的实践，而非一个已发布的产品。 关键词：可量化 benchmark、工具封装、模型投票、算力约束、无背景跨领域。

说明：该分享为现场口述，汇总页未附公开仓库、论文或复现实验链接，「超过资深算法科学家两个月的成果」缺少 benchmark 定义、数据集划分与对照组配置。核查 github.com/Peterleixx 用户页（2026-11-09）可见 6 个公开仓库，均为入门教程、Waypoint SDK 入门模板、OpenAI 兼容 API 客户端、Markdown 报告等，没有与该检测任务对应的仓库、代码或实验记录；页面未列出姓名、组织、个人站点与联系方式，博客与 X 账号未能确认。以下对方法的分析基于汇总页列出的三条做法；涉及效果的部分一律按未经独立验证处理。

他讲了什么

Peter 让 AI Agent 在一台 MacBook 上自主研究两天，做出的 AI 生成图与 PS 痕迹识别模型，效果超过资深算法科学家两个月的成果。方法有三条：

  1. 设一个可量化的 benchmark 作为迭代目标；
  2. 把推理平台的能力封装成工具交给 Agent 调用；
  3. 算力不足时不做训练，改用多个公开模型投票并调整权重。

关键点拆解

第一，benchmark 是整套方法的支点。 Agent 自主研究最大的障碍不是不会写代码，而是不知道「做得更好」具体是什么。没有可自动计算的标量目标，自主迭代就退化成随机游走：每一步都能自圆其说，但没有方向。把任务翻译成一个能跑出分数的评测，等于给 Agent 装上了梯度。这也是本期最反复出现的动作——JJ Ying 给字体建五维量表、Hao 把咨询输出准确率从 80% 提到 95%、David Jiang 把课标拆成可检查的知识点，本质上都是先把「好」定义成可测的东西。

第二，把推理平台封装成工具，是「能力接口化」。 不是让 Agent 读文档、自己拼底层 API，而是给它一组语义明确的调用：跑一次推理、取一次特征、算一次指标。这样既降低了上下文负担，也把错误收敛到工具边界内。它与本期 Colleen 用 MCP 暴露市场研究能力、monid.ai 用一个 skill 接 2900 多个工具，以及第一期 yytyyf 的 KeyKeeper「可用不可读」，是同一条思路的不同实现：给 Agent 的不是权限，是动作。

第三，「不训练、改投票调权」是算力约束下的正确取舍。 训练需要数据、显存与时间；集成只需要推理。更关键的是搜索空间的大小：权重是少数几个可调参数，优化空间小，小样本下更容易收敛，适合 Agent 在两天里反复试错。这是用搜索空间换算力，而不是用性能换便利。

第四，「超过两个月成果」需要谨慎解读。 缺少公开指标、数据集与对照组，结论无法独立验证；「两个月」也可能包含调研、工程化、部署、写文档等非模型指标工作。这条经验真正证明的是「领域门槛可以被跨越」，不是「AI 超过专家」。把它当成方法可行性的信号更合适。

第五，无背景既可能是优势，也划定了风险边界。 不会被「应该先训个模型」的惯性绑定，因此更容易接受投票 + 调权这种不体面但有效的方案；但同时也难以判断统计显著性、是否过拟合到验证集、以及检测任务在真实分布上的漂移。外行能跨过实现门槛，跨不过评估门槛——这恰好是第五部分要展开的判断。

第六，隐性门槛在「选对 benchmark」。 指标定义错了，Agent 会非常高效地优化一个错误的量（古德哈特定律）。选指标这一步仍然完全依赖人的领域判断，且无法自动化。

可迁移的方法

  1. 启动自主 Agent 任务前，先定义可自动计算、可反复比较的标量目标。
  2. 把平台能力封装成语义明确的工具，别让 Agent 自己拼底层接口。
  3. 算力受限时优先搜索集成权重，而不是启动训练。
  4. 用「目标 + 约束」补领域经验的不足，但保留对指标有效性的独立复核。

边界与提醒

无公开材料、无复现实验，所有效果描述应视为现场经验而非技术结论。集成方法的收益高度依赖公开模型之间的差异性，模型同质化时投票几乎无效；在两天内反复试同一个验证集，本质上是在对验证集过拟合。此外，AI 生成图检测与 PS 痕迹检测是典型的高漂移任务——生成模型每迭代一次，旧特征的判别力就衰减一次，实验室指标与线上表现常有明显落差。

03 Hao：咨询报告与 PPT 交付的 skill 化

相关链接主页 · goodinsight.aiBrand Logo Finder

身份：goodinsight.ai，做咨询报告与 PPT 交付。 分享对象：一套把咨询经验拆成标准化 skill 的 AI 工作流，以及已开源的 Brand Logo Finder。 关键词：skill 化、执行成本、交付周期、报价重构、来源证据、人工复核。

他讲了什么

Hao 现在每月在 AI 上花费约 1000 美元，AI 承担约 95% 的执行环节，交付周期从两周缩短到两天，报价降至原来的三分之一到五分之一。

做法是把咨询经验拆成标准化的 skill，并对高频场景单独优化，把输出准确率从约 80% 提高到 95% 以上。其中查找品牌官方 logo 的 Brand Logo Finder 已经开源，它会保留来源证据，把不确定的结果交给人工复核。

核查说明：goodinsight.ai 实际是 Substack 上的「好AI营销周报」，站点上没有上述 1000 美元、95%、两周→两天、报价 1/3~1/5、80%→95% 等任何数字，因此这些均为现场口述，无公开页面佐证。真正可核实的是 Brand Logo Finder 仓库（作者 Hao Wu / GoodInsight.Ai，MIT，Python 3.10+，需 Pillow 与 curl_cffi），其 README 自述是 "A small Agent Skill for a deceptively difficult task"，做的是 "Source-traceable brand logo collection with explicit identity review and image-bound QC"，并声明这套公开版"从 HaoLifeLab 私有品牌资产工作流中提取了身份、图像与验收约束"。

Brand Logo Finder 的可核实机制：输入 companies.csv 与 input/brands.json → helper.py fetch/fetch-plan 按 manifest 逐条取图 → 输出 output/report.json、contact sheet 与全尺寸图 → reviews.json（人工确认品牌身份与授权）→ review → qc。三条硬约束写得很清楚："Downloaded successfully does not mean correct brand."、"Pin every review to the current image SHA-256"（复核绑定到图片哈希，换图即失效，防止复核与文件错配）、"Missing, failed, uncertain and unreviewed items block QC"（缺失、失败、存疑、未复核一律阻断验收）。退出码分三级：0 为全部通过，2 为待复核或 QC 失败，1 为输入或运行错误——「需要人工」被编码成了可被 CI 识别的退出状态。仓库还明确写了边界：无需私有 API Key、没有隐藏搜索服务、不自动保证品牌身份；确认官方域名/市场/子品牌、SVG 转换、历史或地区版本取舍、去不透明背景、判断是否为真实品牌，都留给人或 Agent。

关键点拆解

第一，四个数字构成一条完整的商业链条。 成本（1000 美元/月）→ 执行占比（95%）→ 周期（两周→两天）→ 报价（1/3~1/5）。值得注意的是报价降幅明显大于周期降幅：如果降价只是效率传导，两者应大致同比例。更大的降幅说明这是一次主动的商业模式重构——用交付频次与可及性换单价。AI 提效之后最容易被忽略的决策恰恰在这里：效率红利可以留在利润里，也可以换成订单量，Hao 选了后者。

第二，「把咨询经验拆成标准化 skill」是本期最典型的知识工程动作。 咨询公司的核心资产是方法论与判断套路，过去存在于顾问脑子里、靠带教传递。写成 skill 意味着它可版本化、可复用、可交给模型执行、可针对场景做 A/B 优化。80%→95% 的来源不是换了更强的模型，是把经验写成可检查的步骤——这与 Peter Lei 的 benchmark、JJ Ying 的量表是同一件事在不同行业的形态。

第三，「对高频场景单独优化」承认了通用 skill 的上限。 从 80% 到 95% 的最后一程，通常不是通用能力不足，而是长尾场景缺乏专门处理。这与软件工程里「先搭通用框架，再对热点路径优化」同构，也解释了为什么「拆成 skill」比「写一条长提示词」更可持续：拆开之后才能单点改进、单独评估。

第四，Brand Logo Finder 的两个设计比功能本身更值得看。 保留来源证据，让每个结论可追溯到具体页面；把不确定结果路由给人工，让「模型会错」变成一个显式的流程分支，而不是一句免责声明。本期至少三个案例在做同一件事：Comma 的待审核队列、小禾的医桥中国「人工复核后才发客户」、以及这里的低置信路由。共同模式是：在自动化输出侧保留一道人造闸门，且闸门由置信度触发，而非由人主动巡检。

第五，降价之后成本结构变紧了。 每月约 1000 美元的 AI 支出是相对固定的，报价降到 1/5 意味着必须靠单量上升才能维持收入。这套模式对「按需交付、可标准化」的报告类业务成立，对「按人天计费、高度非标」的驻场咨询很难套用。

第六，剩下那 5% 是什么，决定了这门生意的性质。 汇总页没有明说，从上下文推断应当是需求澄清、关键判断、客户沟通与最终把关。若真如此，咨询费的定价基础就从「工时」转向了「判断」——与第一期横向总结第五条「瓶颈从执行转移到判断」完全吻合，只是这一次它被写进了报价单。【推断】

可迁移的方法

  1. 把领域经验拆成可版本化、可单独优化的 skill，而不是依赖即兴提示词。
  2. 为高频场景单独处理长尾，别指望一条通用流程吃下全部情况。
  3. 输出必须带来源证据，并把低置信结果自动路由给人工。
  4. 提效之后主动决定红利去向：留利润、降报价，还是换交付频次——三种选择对应三种商业模式。

边界与提醒

所有数字为分享者自述，无第三方核实；「准确率 80%→95%」的评测口径、样本量与错误类型未公开。咨询质量中有大量不可自动评估的成分（洞察、叙事、客户语境、政治因素），准确率指标很可能只覆盖可结构化的那部分。skill 化会把方法论固化，市场结构或客户类型变化时，固化经验反而成为惯性。此外，报价降至 1/5 会重塑客户对服务价值的预期，长期议价能力存在被压缩的风险；整套流程还依赖第三方模型的价格、可用性与输出稳定性，上游调价会直接改写成本模型。

04 Colleen：SpringBrand 与 MCP 分发

相关链接主页 · linkedin.com/in/kejing-ySpringBrand报告

身份：linkedin.com/in/kejing-y，SpringBrand 团队。 分享对象：通过 MCP 接入各类 Agent 的市场研究与内容工具，以及一份样例品牌分析报告。 关键词：MCP、能力分发、社媒数据、推算口径、模型行为对比。

他讲了什么

SpringBrand 通过 MCP 接入 Claude、ChatGPT、Cursor 等 Agent，提供市场研究、获客和内容工具，可抓取小红书等平台的数据并生成品牌分析报告。一份样例报告根据公开数据推算，Teamily 一个季度注册量增长 32 倍，主要来自两轮付费投放。

现场还演示了让多个大模型同桌打德扑和麻将，用来比较各模型的行为。

公开页面补充（springbrand.ai，2026-11-09 可访问）：官网列出的「实证优先」数据源包括 Google Search、Semrush、Ahrefs、TikTok、Instagram、YouTube、Apollo、Google Maps、Amazon，以及 Reddit、TikTok 论坛、X、小红书等讨论区——汇总页提到的「微博」未出现在官网数据源中。MCP 侧提供 discover-then-run 五件套：search_tools / get_tool_schemas / execute_tools / get_execution / manage_connections，按 Credits 计费，注册有 300 免费额度（最多 20 个任务）；列出的客户端包括 Claude Code、ChatGPT、Cursor、OpenClaw、Hermes Agent、WorkBuddy 与 DeepSeek Harness。

样例报告本身比汇总页更谨慎：它把每条结论标成四级证据——Verified source on record / Inferred / Disputed / Company-reported unverified。「32× 增长」在报告里被明确标为 Company-reported unverified，来源是 Summer Chen 的长帖《32× Growth in One Quarter With a Small Team》（2026-11-03），报告还注明「该季度的日期与其他已报数字对不上」；「两轮投放驱动增长」标为 Inferred，第二轮更是写明「该步骤大部分没有可识别来源」。报告的落款建议是："Copy the tactics, not the numbers. Pressure-test the channel attribution..."

关键点拆解

第一，MCP 在这里不是技术选型，是分发决策。 SpringBrand 没有自建 UI 工作流，而是把能力挂到用户已经在用的 Agent 上。获客成本因此变成「被接入的成本」，产品也不必与 Claude、ChatGPT 争夺用户入口。把它和第一期 Ego Lite 用 Skill 而非 SDK 接入、本期 monid.ai 用一个 skill 接 2900 多个工具放在一起，能看出一条清晰的路径：能力型产品的接口正在从「给人用的界面」变成「给 Agent 用的能力描述」，集成成本从 N×M 压到 N+M。

第二，「抓数据 + 生成报告」的价值不在抓取，在证据分级。 从公开信号反推一个产品的季度注册量增长 32 倍，这是估算而非事实。但这份报告的处理方式值得肯定：它没有把估算写成结论，而是给每条论断打上四级标签，把「公司自报未经核实」「推断」「有争议」与「有来源可查」分开，甚至主动指出季度日期对不上、第二轮投放缺乏来源。这比给出一个漂亮数字难得多，也更能进 B 端决策流程——第一期为 Ego Lite 厂商自测数字定下的原则是「给出对照与口径，数字才有意义」，这里是同一原则的更高配版本：给数字标可信度等级。

值得单独指出的是，汇总页写「根据公开数据推算，Teamily 一个季度注册量增长 32 倍，主要来自两轮付费投放」，语气比原报告肯定得多。信息在转述中被抹平了不确定性——这恰好是阅读这类活动汇总时最需要警惕的一层损耗：现场一句话、汇总页一句话、原始页面一句话，三者的置信度并不相同。

第三，「让多个大模型同桌打牌」看似闲笔，实则是一次很聪明的能力展示。 德扑与麻将都有不完全信息、诈唬、风险偏好与对手建模，在同一规则下横向比较，比列一串 benchmark 分数更直观地暴露模型的行为倾向。它也是一种产品叙事——用可观察的对比，替代抽象的能力宣称。

第四，数据合规是这个产品的结构性约束，不是运营细节。 小红书、微博等平台的数据获取受服务条款与个人信息保护规则限制，「技术可抓取」与「商业可合法使用」是两件事。第一期横向总结的第三条判断是「合规与授权正在成为技术方案的一部分」，这里正好是它的反面教材式提醒：当产品能力建立在第三方平台数据之上，平台策略变化会直接改写产品边界。

第五，MCP 分发的隐含代价是失去用户上下文。 用户与 Agent 的对话历史、意图、反馈都留在宿主侧，SpringBrand 看到的是一次次相对孤立的工具调用。这会影响个性化、迭代依据与留存数据的积累，也意味着产品的品牌被弱化成了「Agent 里的一个工具」。

可迁移的方法

  1. 能力型产品优先接入用户已有的 Agent，而不是新建入口。
  2. 报告类输出明确区分「抓到的事实 / 推算 / 判断」三层，并给出推算依据。
  3. 用同一规则下的横向行为对比展示模型差异，比堆分数更有说服力。
  4. 把数据来源合规当作产品边界设计，而非上线后的补丁。

边界与提醒

Teamily「一个季度增长 32 倍」在原报告中被标为 Company-reported unverified（公司自报、未经核实），不是由公开数据独立推算所得，且报告自陈季度日期与其他数字对不上；「两轮投放」为推断，其中第二轮缺乏可识别来源，不应作为事实引用。社媒数据抓取的合规性与稳定性随平台策略变化，接口改版会直接影响报告质量；官网数据源列表中未见「微博」，汇总页这一项未能核实。MCP 协议与宿主 Agent 的策略均属外部依赖，产品对自身可用性的控制权有限；此外，通过第三方 Agent 分发时，用户对「哪些数据被传给了谁」的感知更弱，隐私告知义务反而更重。

05 Sean Shao：一句放在全局上下文开头的提示词

相关链接主页 · x.com/hopsken幻灯片

身份：x.com/hopsken，现场幻灯片本身是一个可以翻阅的网页。 分享对象：一段 Agent 全局提示词及其使用中的观察。 关键词：领域路由、抑制首答、上下文溢出信号、MoE、可观测性。

他讲了什么

提示词原文：

don't act on your first thought, always start your thinking by "as a senior engineer / designer / role based on the task, i would"

Sean 的解释是：MoE 模型由分管不同领域的「专家」组成，先让模型判断任务所属领域、再以该领域资深角色作答，可以调出对应的知识；这对 Opus 5.5 同样有效。另一个观察是：模型不再输出「As a senior…」时，通常说明上下文即将溢出，需要压缩或拆分任务。

关键点拆解

第一，这句提示词同时做了两件事。 don't act on your first thought 抑制首答冲动，start your thinking by... 强制领域路由。与常见的「你是 XX 专家」式系统提示相比，关键差别在于把角色放进思考的开头，而不是答案的开头——它约束的是推理路径，不是输出语气。

第二，「MoE 专家按职业分工」这个机理解释需要修正。 MoE 的专家是训练得到的子网络，按 token 隐式激活，并不对应「工程师」「设计师」这类人类职业分工；系统提示影响的是模型的条件分布与注意力，不能理解为手动指定激活哪几个专家。因此更准确的说法是：这是一个有效的提示词工程技巧，但它背后的架构解释不成立。分享者自己补充「对 Opus 5.5 同样有效」，恰好构成反证——若机制真的来自 MoE 专家路由，就难以解释在非 MoE 或不同架构模型上的一致性效果。更合理的解释是：给定明确专业身份后，模型会向该身份对应的语料分布靠拢，减少泛泛而谈，这属于条件化效应，与架构无关。【分析，且与汇总页给出的机理解释有分歧】

第三，最有工程价值的是那句溢出信号。 把「模型不再复读 As a senior…」当作上下文即将失效的可观测指标，是一种很朴素的格式金丝雀：系统提示位于上下文最前端，当它被截断、被稀释或被后续内容压过时，最先消失的往往就是这类开头格式约束。这比等模型明显变笨、开始答非所问再排查要早一步，也与本期 0xinhua「去看真实日志而不是猜」是同一种实证取向。

第四，但这个信号的特异性不足。 模型不输出该前缀，也可能是因为它学会了省略、换了表述、任务类型不适合角色化，或系统提示被宿主 Agent 改写。它是提示，不是诊断，应配合其他信号一起判断：开始遗忘早期约束、工具调用格式出错、重复追问已给过的信息。

第五，「放在全局上下文开头」隐含一个工程前提：上下文必须可控、可压缩。 如果会话无限增长且没有压缩机制，这类前缀技巧的收益会随长度衰减。所以这条提示词与「发现信号就压缩或拆任务」是一套动作，不能只抄前半句。

可迁移的方法

  1. 在全局提示里同时写「先思考」与「按任务选领域角色」，而不是只声明一个固定身份。
  2. 给长会话设一个可观察的格式金丝雀，用来提前发现上下文退化。
  3. 出现溢出信号时优先压缩上下文或拆分任务，不要继续追加指令。
  4. 对提示词技巧的机理解释保持怀疑：有效 ≠ 解释正确，用 A/B 实测判断，不用架构故事判断。

边界与提醒

效果为分享者的现场经验，未给出对照实验、任务集或量化指标；不同模型、不同系统提示模板对前缀约束的遵守程度差异很大，换模型后需重新验证。「MoE 专家按领域分工」不是对 MoE 机制的准确描述，不应作为技术结论引用。格式金丝雀存在假阳性与假阴性，不能作为唯一判据。此外，强制角色化在某些任务上（需要中立、需要承认不确定、需要跨领域综合）反而可能引入偏见，应允许按任务类型跳过。

第二部分 · 筛选权：拿回来，以及被 AI 选中

这一部分的五个分享看似分散——RSS 阅读器、论文推荐、字体打分、ChatGPT 日志、llms.txt——其实在讲同一场变化的两面：人在把筛选权从平台手里拿回来，同时又在争取被 Agent 选中。前者是自己做推荐系统，后者是让自己成为别人推荐系统的候选。当调用方从人变成 Agent，这两件事就合并成了同一个问题。

06 Owen：个人 RSS 阅读流程

相关链接主页 · owenyoung.comNetNewsWireMiniflux

身份：owenyoung.com，Tab 星期四联合发起人。第一期分享的是 Good Enough 团队与产品理念，本期分享的是自己每天在用的一套流程。 分享对象：中文源用 NetNewsWire，英文源用自部署 Miniflux，配合自定义 JS 与沉浸式翻译。现场另有参与者推荐 Mac 划词翻译工具 Bob。 关键词：筛选前移、分流工具链、自部署、译文只用于 triage、可审计。

他讲了什么

中文来源用 NetNewsWire 订阅；英文来源用自部署的 Miniflux，通过自定义 JS 在列表中直接显示摘要，再用沉浸式翻译把标题和摘要译成中文，不点开文章就能筛选。

现场补充：Bob 是一款 macOS 菜单栏翻译与 OCR 工具，支持划词（默认 ⌥D）、截图（⌥S）、输入翻译（⌥A）与 PopClip，最多同时开启 10 个翻译服务、支持 30 多种服务（Apple、火山、腾讯、阿里、百度、有道、Google、Microsoft、DeepL、OpenAI 等），OCR 支持 macOS 11+ 离线识别、连续识别与二维码。其官网未列定价、开源仓库或许可证，第三方说法互相矛盾，此处不采信。

关键点拆解

第一，「不点开文章就能筛选」是这套流程的目标函数。 常规 RSS 的结构是「列表 → 点开 → 判断要不要读」，判断发生在打开之后；Owen 把摘要与译文提前到列表层，等于把筛选前移一层。省下的不是阅读时间，是「打开—发现不值得读—退回」的切换成本。信息量大时，切换成本远大于阅读成本。

第二，中英文分两个阅读器，是承认处理链路不同。 中文源不需要翻译，用轻量原生客户端即可；英文源需要摘要、译文与自定义 JS，必须自部署才改得动。按处理需求分流，而不是为了统一而统一——这与第一期 CC 的「可替换工具链」是同一套思路：每个环节选刚好合用的工具，保留随时换掉的能力。

第三，自部署的核心收益是「界面可写」。 托管型 RSS 服务（Feedly、Inoreader）不允许改列表渲染，用户只能接受厂商给的摘要长度与排版。Miniflux 把「列表长什么样」变成可以自己写的代码。代价是运维自己扛——这恰好是第一期 Owen 自己讲过的「小团队要把运维成本当一等约束」的另一面：这次他把运维成本收在个人身上，换的是完全控制权。

第四，译文只用于筛选时，质量要求可以下调。 沉浸式翻译在这里不是「读英文」，而是「用母语扫一遍标题和摘要，只对少量条目进入原文」。既然译文服务于 triage 而非理解，那么用质量换离线、速度与零成本就是划算的。这与第 19 章 Transparent 默认调用 macOS 自带本地翻译模型「代价是译文质量」是同一个判断，两章互为注脚：先确定译文在服务哪一步决策，再决定值不值得上大模型。

第五，与第一期第 18 位 imxiaorong 形成一组耐人寻味的对照。 两者都在把目标函数从平台手里拿回来：一个用模型训练个人偏好，一个用规则与工具链手工搭筛选层。Owen 的方案不需要训练数据、不需要模型，排序是时间序、源是自己选的，因此也不构成新的过滤气泡（尽管仍有「信源自选」带来的气泡，见边界）。在模型方案流行的当下，一个不用模型的方案反而更可审计——每一步为什么筛掉，都能指回具体规则。

第六，两套翻译工具是分层而非竞争。 列表层用沉浸式翻译做批量筛选，正文层用划词翻译做点状查询。粒度不同、触发方式不同，不互相替代。工具链的价值往往就体现在这种分层，而不是单个工具多强。

可迁移的方法

  1. 先写清楚信息流要服务的决策，再把筛选动作尽量前移到列表层。
  2. 按处理链路分流工具，别为了统一牺牲某一类内容的处理质量。
  3. 当译文只用于筛选时，大胆用本地/廉价模型换离线与成本。
  4. 自部署之前先确认「我到底要改什么」，只为一处可控改动承担运维才划算。

边界与提醒

摘要与译文前移会放大标题党效应与摘要偏差，容易因摘要写得平淡而错过长文里的关键论证。自定义 JS 依赖 Miniflux 的 DOM 结构，版本升级可能失效。时间序 + 自选自源意味着没有发现新信源的机制，信源列表会随时间老化，且自己选源本身就是一种过滤气泡——第一期 imxiaorong 那章已经指出，自建气泡比平台气泡更难察觉，因为它是自己喂出来的。此外，不少站点只提供截断摘要甚至仅标题，流程对这些源直接失效；机器翻译在专业术语、否定结构与双关上误译率较高，筛选时应保留「拿不准就点开原文」的习惯。

07 Yorkson：ZotWatch 与两级筛选

相关链接主页 · blog.yorks0n.comZotWatch

身份：blog.yorks0n.com，github.com/Yorks0n/ZotWatch。 分享对象：基于个人 Zotero 文库的每日论文推荐，以及同一套结构复用到资讯处理。 关键词：粗排 + 精排、私有算力、Top-K 上限、下游行为建模、稍后读。

他讲了什么

ZotWatch 根据用户的 Zotero 文库建立兴趣模型，每天从新发表论文中推荐最多 30 篇，通过网页和 RSS 发布，计算在用户自己的私有 GitHub 工作空间里运行。

筛选分两步：先用轻量的文本嵌入模型从数千篇中挑出几十篇，再由大模型精选。Yorkson 用同样的结构处理资讯：多个 Bot 分别汇总 Hacker News、Reddit 和 X，再由一个 Bot 挑出值得深读的内容，生成 HTML 导入稍后读。

仓库与博客补充（GitHub 与 blog.yorks0n.com，2026-11-09 可访问）：README 明确写「计算在你自己的私有 GitHub 工作空间中运行，公开结果发布到独立仓库」，与汇总页表述一致；架构拆成 zotwatch-web（私有源码，Web + Cloudflare Worker）、zotwatch-workspace-template（私有）与 zotwatch-public-harvester（公共论文元数据采集/去重/API）三部分，用户不需 Fork 引擎仓库、也不需要自行部署公共采集服务。

几处比汇总页更精确的限定值得记下：「最多 30 篇」是上限而非保底，README 写明「候选不足或数据源异常，都可能导致未就绪、少量推荐或空结果。系统不会为了凑齐数量而静默降低模型要求」；基础推荐不需要 AI Key，新用户的 AI 功能默认关闭，README 写「基础推荐使用文库语义与兴趣中心，AI 发布处理在原推荐列表之后执行」——也就是说「大模型精选」并非基础两步筛选的必备环节，而是可叠加的一层。翻译与判断走 optional-llm.yaml（provider: none/llm/jev、max_items: 20、timeout_seconds: 120），嵌入模型只称「固定编码器（a pinned encoder）」，未给名称。项目为 MIT、Python 3.11+、包版本 2.0.0.dev1。

作者博客补充了工程演进：早期版本用 TextVectorizer → FAISS 索引，数据源为 Crossref、arXiv、bioRxiv/medRxiv，叠加 ScimagoJR 期刊 SJR 质量、时效性与作者加权，默认输出 20 篇、只保留近 7 天文章、预印本比例不超过 30%，GitHub Actions 每天早上 6 点跑并发布到 GitHub Pages + /feed.xml；2026-10-21 记「一千多篇文献大概需要运行十五分钟」。2026-11-06 的 Grok Bot 文章则给出了汇总页「两步筛选」的原文依据：「每天可能不同领域几千篇新文章，token 消耗量巨大。先经过一个小模型的文本嵌入…拿到相关但质量不完全那么好的几十个候选，然后再让语言模型处理就比较轻松了」；资讯侧是 Reddit 摘要（早八点）、推特精选（晚八点）、Hacker News 热帖、游戏资讯 Bot，另有一个 Bot「从中挑选两条深挖」。另需注意：V2 开发文档（2026-10-16）自陈「本次没有运行真实用户文库、AI 计费调用或线上端到端验收」。

关键点拆解

第一，两级筛选是推荐系统的标准架构，但缩放到个人规模才是关键。 数千篇里先用便宜的嵌入模型召回几十篇，再让贵的大模型精读，贵模型的调用次数被压成一个由便宜模型决定的小常数。这是所有个人 AI 工具的成本控制通则：不要试图让一个模型既便宜又聪明，而是用便宜模型控制聪明模型看多少东西。第 08 章 JJ Ying 遇到的「Gemini 快但 OpenAI 准却易超时」，也可以用同一结构化解。

第二，用 Zotero 文库当兴趣模型，是选对了信号源。 文库是用户主动收藏、大概率认真读过的内容，比点击、停留这类隐式行为干净得多。这正是第一期 imxiaorong 那章给出的判断——优先采集下游动作（引用、使用、改变决定），而不是上游浏览——的落地实现。Zotero 文库几乎是可得的最强下游信号之一。

第三，「每天最多 30 篇」是产品决策，不是技术参数。 它把系统从「尽可能多推」改成「在固定预算内选最好的」，排序因此变成一个明确的 Top-K 选择问题，人的阅读负担也被固定住。这与第一期 Cassie 的 1Day 用 2 秒硬约束换习惯、花卷用编号与卷册限定收录量是同一种手法：主动设上限，反而让系统可用。

第四，「私有 GitHub 工作空间」这个位置选得巧。 GitHub Actions 提供现成的定时调度，仓库可以私有，输出又能直接通过网页或 RSS 交付——等于借成熟基础设施跑了一个零服务器运维的个人推荐服务。代价是调度粒度、超时与配额都受平台约束，且策略变化不在自己控制内。这与第 16 章 Occupy SaaS 的「谁来维护」是同一个问题的两面：借别人的基础设施省了运维，也交出了一部分控制权。

第五，同一套结构复用到资讯，说明作者抽象出了母题。 「多源采集 → 分层筛选 → 固定格式交付」被同时用在论文与资讯两个领域，与第一期 David Jiang「用一个母题做多个作品，换领域不换方法」完全一致。本期 David Jiang 自己又换了领域（从词向量到课标技能树），两个人用不同题材印证了同一条工作方法。

第六，Zotero 文库有一个结构性偏差：它记录的是你过去感兴趣的东西，不是你现在想突破的方向。 用历史拟合兴趣，会稳定地收窄视野；嵌入模型又天然偏好「与已有文献语义相似」的内容，进一步压制跨学科与反直觉发现。这是所有基于历史偏好的推荐共有的气泡，只是这次由自己亲手喂养。【分析】

可迁移的方法

  1. 两级筛选：便宜模型负责召回，贵模型只处理候选集，用召回量控制成本。
  2. 用主动收藏、引用、使用等下游行为建模，别用点击与停留。
  3. 给每日推荐设硬上限，把排序变成预算内的 Top-K 选择。
  4. 借现成的定时任务与托管平台跑个人服务，别自己养服务器。
  5. 为「探索」单独留通道，防止历史偏好把视野收窄。

边界与提醒

Zotero 文库质量直接决定推荐质量：长期不整理、混入大量未读条目时，兴趣模型会失真。新论文源若覆盖不全（例如只覆盖 arXiv 等预印本），会系统性漏掉某些学科。GitHub Actions 的调度延迟、超时与配额会影响「每天」的稳定性，私有仓库与 Pages/RSS 的组合也随平台政策变化。「最多 30 篇」是作者设定的带宽，未必适合所有人。最需要主动对抗的是探索性缺失——若不加异质源或反事实提问，这套系统会非常高效地把你留在已知领域里。

08 JJ Ying：给字体品味建一个五维坐标系

相关链接主页 · twitter.com/jjying幻灯片

身份：twitter.com/jjying，字体预览工具 Anyway.Fonts，现场幻灯片本身是一个可以翻阅的网页。 分享对象：用大模型给字体打分、据此推荐相似字体的方法。 关键词：双极量表、屏蔽先验、参照锚点校准、长文档超时、可翻阅的演示物。

他讲了什么

每款字体按古典/现代、规整/自由、柔和/硬朗、几何/书写、朴素/装饰五个维度打 1 到 9 分，在五维空间里按距离找邻居。模型只看合成在一份 PDF 里的样张，不看字体名。

不同模型、甚至同一模型的不同版本，给出的分数并不一致，因此提示词必须给出参照，例如「现代正文宋体约 4 分」。Gemini 处理大 PDF 更快，OpenAI 的模型更准但容易超时。

核查说明：anyway.fm/fonts/tab/ 页面可访问，但正文由前端渲染，静态抓取只能拿到标题「用 AI 探索字体风格与相似度 · JJ Ying」与署名「UI 设计师 · Anyway.FM 主播」；Anyway.Fonts 本体是字体预览工具页，支持缺字检测、竖排、海报样张、最多四款并排对比，声明「无需安装、无需登录」，字体文件在本地浏览器解析、不上传服务器。因此上述五个维度、参照锚点与 Gemini/OpenAI 对比均为现场口述，公开页面上没有可读佐证；本文对方法的分析以汇总页记录为准，不把幻灯片当成可复核的数据源。

但「给字体做结构化比较」这件事本身有公开的产品底座：Anyway.Fonts 已经在做并排对比与样张渲染，字体打分是在这个已有的比较界面之上，补一层「按什么维度比、怎么找邻居」。也就是说，先有可比较的载体，再谈可计算的相似度——这个顺序值得留意。

关键点拆解

第一，把「字体品味」拆成五个可打分维度，是整个方案最关键的一步。 品味本来是不可言说的整体判断，一旦拆成分量，就变成五维空间中的坐标，「相似」也就有了可计算的定义。这是把隐性判断显性化的教科书案例：不是让模型直接说「这两款字体像」，而是先定义「像」在哪些维度上成立。本期至少五个案例在做同一件事，这条线索会在第五部分展开。

第二，五个维度都是双极量表而非单极量表。 「古典 ↔ 现代」比「现代程度」稳定得多：两端有明确锚点，中间值有含义（4–6 分表示两者都不极端），还能表达风格张力。单极量表容易让模型把所有字体都往中间堆，双极量表迫使它做相对判断。

第三，「不看字体名」是防止先验污染的控制变量。 字体名带有强烈的品牌与历史联想（Helvetica、思源宋体），模型一旦看到名字，打的就是对名字的印象而不是对字形的观察。这与第一期第 17 位天天讨论「隐喻评估」有结构上的相似：要评估的是映射本身，不是标签带来的联想。【分析】

第四，「不同模型、甚至同一模型不同版本分数不一致」是这次分享最诚实的发现。 它说明绝对分数没有意义，只有同一模型、同一提示词、同一批次内的相对关系才可用。参照锚点（「现代正文宋体约 4 分」）的作用是把浮动的量表钉在共同基准上——工程上这叫校准，不是提示词技巧。由此还能推出一个更严格的做法：字体库应一次性全量打分并固化，而不是每次查询实时打分，否则同一款字体的坐标会漂，邻居也跟着漂。汇总页未说明是否固化，这是实现上的关键分岔。【推断/建议】

第五，Gemini 快、OpenAI 准但易超时，是速度—质量—稳定性的三角。 合成了全部样张的 PDF 会很长，长上下文下超时概率上升。可行解不止一个：分批送入、缓存逐款打分结果、或让快模型批量初筛 + 慢模型复核——正好是 ZotWatch 那套两级结构换了个场景。

第六，幻灯片本身做成可翻阅的网页，形式与内容自洽。 讲一个关于「可翻阅、可比较」的工具，载体也是可翻阅的。第一期花卷的集邮册、JJ Ying 的幻灯片，都属于「演示物即论证」的做法：不解释品味，直接让人体验。

可迁移的方法

  1. 让模型做主观判断前，先把判断拆成双极量表维度。
  2. 屏蔽名称、品牌等先验标签，只给模型看被评估对象本身。
  3. 用参照锚点校准量表；只信同批次内的相对关系，别信绝对分数。
  4. 打分结果固化缓存，避免模型版本变化导致坐标漂移。
  5. 长文档按「快模型批量 + 慢模型复核」分层，别硬扛超时。

边界与提醒

五维是否足以刻画字体风格、维度之间是否真正独立，未经公开验证；字重、字宽、字面率、衬线形态、小字号可读性等维度未纳入。打的是「样张观感」，不是字体在真实排版中的表现。分数随模型版本、提示词措辞、PDF 渲染方式变化，跨批次比较不可靠。「相似」被定义为五维距离，隐含各维度等权，而实际使用中不同需求（正文、标题、品牌字）对维度的权重差异很大。此外，样张合成与字体展示涉及授权，商业使用前需确认。

关键点拆解

第一，这个方法的价值在于把「AI 推荐」从玄学变成可观测的过程。 多数 GEO/AI SEO 讨论停留在「猜模型喜欢什么」，这里直接去看模型实际发出的查询与访问过的站点。搜索词是因、访问站点是果、最终回答是输出——三者对齐后，优化才有落点。它与第 05 章的格式金丝雀、第 10 章的 llms.txt 一起，构成本期一条很清晰的取向：不猜，去看日志。

第二，「模型实际扩展的搜索词」尤其关键。 用户问的是一句话，检索系统可能改写、拆分、扩展成多条 query。你的页面若只覆盖用户原始措辞，可能从来没进入候选集。优化对象不是用户的问题，而是模型改写后的问题——这与传统 SEO 里「关键词研究」的差别，在于关键词不再是人猜的，而是可以从日志里读出来的。

第三，四条观察指向同一个机制：降低抽取成本。 带更新时间解决时效判断，准确数字提供可引用的事实点，对比表格本身就是结构化数据，页首摘要适配「只抓取前若干片段」的检索管线。这四条不是讨好模型的修辞，而是让内容更容易被切分、被引用、被验证。它们与第 10 章 llms.txt 写的「用途、人群、定价、与竞品区别」是同一类东西：可被直接引用的事实卡。

第四，与奚圣波、司马光砸缸合起来看，是一条完整链条。 让机器读得懂（内容结构）→ 让机器找得到（抓取许可与检索命中）→ 让机器愿意引（事实密度与可验证性）。0xinhua 提供的是这条链上的观测端：没有它，另外两端只能盲调。

第五，PostPiper 通过 MCP 在 Agent 里起草与排期，让观察与执行形成闭环。 作者既在研究「被 AI 看见」，也把发布动作搬进了 Agent。这与第 04 章 SpringBrand 的 MCP 分发、线上分享里 social-auto-upload 附带的 Skill，是同一个方向：内容的生产与分发正在成为 Agent 可调用的能力。

第六，必须区分相关性与因果。 四条观察是经验归纳，没有对照实验；它们很可能只是「内容质量高」的伴生特征——认真维护的页面恰好既有更新时间又有准确数字，被推荐是因为内容本身好，而不是因为加了表格。这个混淆变量不点破，就容易把「写好内容」误读成「套格式」。【分析】

可迁移的方法

  1. 优化 AI 可见性前，先想办法看到模型的真实检索词与访问列表。
  2. 针对「改写后的 query」布局内容，而不是只盯用户原始问法。
  3. 把可引用事实（日期、数字、对比、结论摘要）放在页面靠前且结构化的位置。
  4. 把分发动作也接到 Agent 上，形成观察—执行闭环。
  5. 对经验规律做 A/B 验证，警惕「内容质量」这个混淆变量。

边界与提醒

该方法依赖网页版 ChatGPT 当前的实现，接口结构与字段随时可能变化，conversation id 与响应 JSON 也非稳定公开 API。不同模型、不同检索后端行为差异大，结论不可直接外推。四条「有助被推荐」为个人观察，无对照组与样本量，属相关性而非因果。过度针对检索词优化容易滑向内容农场式写法，损害真实读者体验与长期品牌。此外，用开发者工具读取响应内容时需留意服务条款与账号合规。

10 奚圣波：绘页的 GEO 实践

相关链接主页 · x.com/xishengbo绘页教程

身份：x.com/xishengbo，绘本视频工具绘页。 分享对象：为绘页做 GEO（Generative Engine Optimization）的三步做法与一次小样本观察。 关键词：robots.txt、llms.txt、触发访问、被引用率、上游不可控。

他讲了什么

  1. 在 robots.txt 中放行 OAI-SearchBot、ChatGPT-User 等 AI 爬虫；
  2. 加入 llms.txt，写明网站用途、目标用户、定价和与竞品的区别；
  3. 再主动与 AI 多轮对话，引导它访问网站。

一个旧站用这种方法在 7 天内获得了 51 次来自 AI 的访问，但见效时间难以预测。方法参考了 Geektao 的教程。

页面核查（huiye.org，2026-11-09）：robots.txt 与 llms.txt 确实存在且可读，做法与汇总页一致，可核实程度在本期分享中属于较高的一档。robots.txt 显式放行 OAI-SearchBot、ChatGPT-User、GPTBot、ClaudeBot、PerplexityBot，并对所有爬虫 Allow: /；llms.txt 以 # Drawnpage 开头，逐项写明产品定位（把故事变成绘本动画视频，五步：写故事 → 一键分镜 → 选画风与音色 → 配音与音乐 → 导出 MP4）、目标用户（儿童内容创作者、家长、老师、出版社、儿童品牌）、定价（Free ¥0 / Creator ¥49 每月 / Studio ¥129 每月 / Enterprise 联系销售，年付约省 20%）、与竞品区别（模板工具、通用 AI 视频生成器、剪映/Canva、儿童绘本 App），以及 Core pages / Tool pages / Contact。首页也把 "GEO Optimization — Get cited by ChatGPT, Claude, Perplexity and Google AI" 列为功能项。

教程与数字的核查：Geektao 教程帖给出的三步法是「先反推 / 后提问 / 再总结」，操作要点包括每次新开对话并打开联网搜索再提问、以及 11 月 4 日的更正——「第 5 步请用临时聊天，只新开对话还是会带上账号记忆」；教程明确「这套做法本身不需要花钱」，还给出时间预期「上线前全部做完，前 3 天 ChatGPT 访问是 0」「新页面上线后最快第二天到」。但「7 天 51 次」在这份教程里没有找到；相近的数字是「改版前 7 天共 12 次 AI 访问」与「2026 年 10 月 ChatGPT 给 7 个站带来 1350 次访问」。因此 51 次应视为现场口述，不能当作该方法公开可复核的效果基准。

关键点拆解

第一，三步对应三个不同层次：放行（能不能进）→ 说明（进来读什么）→ 引导（会不会来）。 robots.txt 解决许可，llms.txt 解决内容供给，主动对话解决触发。只做前两步，可能长期等不到访问；只做第三步，爬虫被挡在门外。这个分层比笼统的「做 GEO」有用得多，也便于逐层排查失败原因。

第二，llms.txt 的内容选择很讲究。 用途、目标用户、定价、与竞品的区别，恰好是模型回答「有什么工具能做 X」「A 和 B 选哪个」「多少钱」时最需要、而营销页最常含糊其辞的信息。它不是给爬虫看的站点地图，是给模型准备的一份可直接引用的事实卡。「与竞品的区别」一项尤其值得注意：它主动进入对比型问题的语境；多数官网回避提竞品，结果模型在对比类问题上只能引用第三方评测。

第三，「7 天 51 次 AI 访问」是一个很小的样本，且分母与归因口径不明。 更值得重视的是作者自己补的那句「见效时间难以预测」——这是整个分享里最诚实的一句，等于承认这套方法对上游索引与检索策略没有控制权，因此给不出 SLA。

第四，「主动与 AI 多轮对话引导访问」的机理存疑。 一次对话中的访问，未必会沉淀成模型在后续对其他用户回答时的引用。它更可能的作用是让检索后端记录到该 URL 的存在，或触发一次即时抓取。短期访问量 ≠ 长期推荐权重，两者不应混为一谈。【分析】

第五，GEO 与传统 SEO 的根本差别在优化对象：SEO 优化排名，GEO 优化被引用。 排名有位置可测，被引用只有出现在回答里的概率。因此效果评估必须基于「在一组固定目标问题上，被提及/被引用的比例」，而不是爬虫访问次数。这一点与第 09 章的可观测性方法正好互补：先用日志确定目标问题集，再用被引用率做长期指标。

第六，与 0xinhua 那章合看，正好是供给端与观测端。 奚圣波在改自己的页面让 AI 读得懂，0xinhua 在拆 AI 到底读了什么。只做一端，优化就是盲的。

可迁移的方法

  1. 按「放行 → 说明 → 触发」三层检查 AI 可见性，别只做其中一层。
  2. 在 llms.txt 里写可直接引用的事实：用途、人群、定价、与竞品差异。
  3. 用一组固定目标问题定期测「被引用率」，而不是看爬虫访问数。
  4. 对上游不可控的效果明确写「无法承诺时间」，避免过度预期。

边界与提醒

llms.txt 目前是社区提议的约定，并非各家 AI 服务承诺遵守的标准，是否被读取取决于具体爬虫实现。robots.txt 放行 AI 爬虫意味着内容可能被用于训练或摘要，需自行评估版权与商业条款。「7 天 51 次」为单个旧站的单次观察，样本小、分母与归因口径未公开，不能作为效果基准。主动引导访问的可持续性未经验证，对话结束后的长期引用权重难以衡量。上游爬虫标识、索引策略与检索后端随时变化，方法有明确时效性。

  1. 建知识结构时先建关系再建清单，边比节点更有信息量。
  2. 给每个节点配一个可执行的验证动作，而不是另加一层考核系统。
  3. 把「我们不做的事」写进产品文档，让克制成为可检查的约束。
  4. 跨体系对齐前先统一粒度，再谈映射，否则关系数据会失真。
  5. 进度数据默认存本地，把主权交给用户（呼应第一期 CC 的 local-first）。

第五，「质量」和「发布时间」这两个维度是一次目标函数声明。 平台推荐优化的是停留时长，质量与时效并不必然服务这个目标；自己写规则，等于先回答「我想要什么」，再写筛选条件。这与第 07 章 ZotWatch 用 Zotero 文库而非点击行为建模，是同一个原则的不同实现。

  1. 学习习惯坚持不下去时优先换媒介，而不是加打卡、加提醒、加意志力。
  2. 生成成本失控时，把任务拆成「素材生成 + 代码组装」，让代码承担一致性。
  3. 目标明确的筛选需求优先用可审计的规则，别急着上偏好模型。
  4. 写自定义推荐之前先写清楚自己的目标函数，再选维度。
  5. 对外讲述时区分「自用实验」「演示样片」「已产品化」三种状态。

  3. 被动干预适合无法主动配合的场景（睡眠），主动干预适合有反馈通道的场景。

关键点拆解

第一，「默认关注全部 1000 人」是最激进的一步，也是「没有推荐算法」得以成立的前提。 它把「关注」从筛选动作改成默认状态，于是所有读者看到的是同一条流。这里真正的机制是用规模上限换掉排序算法：1000 人 × 有限的发布量，信息量小到可以全看，排序就不再必要。没有推荐算法不是功能缺失，是容量设计的结果——反过来，任何声称「我们不用算法」却不限定容量的产品，最后都会悄悄加回某种排序。

第二，筛选权交给了有声誉成本的人。 second / counter 是公开的质量信号，且只有持席位的 1000 位创作者能发。这与普通点赞有本质差别：点赞匿名、零成本、读者可刷；附议与反驳具名、带立场、会影响自己在同侪中的声誉。把筛选权交给有代价的人，信号质量会上升。

第三，「读者的回复单独放在下一层」是一次分层。 创作者层做策展（附议/反驳），读者层做讨论（answer），两者不共用一条时间线。这解决了社交产品的经典问题：热门内容的评论区会与内容本身争夺注意力，最后讨论盖过判断。把「评价」与「回应」拆成两层，等于承认它们不是同一种行为。

第四，收入千等分 + 席位轮换，把分配关系写成了一条固定规则。 尤其值得注意的是 "while you hold the seat" 与 "Yours until the seat turns over"：收益跟随席位流转，席位到期就转移给下一位。这让「1000」不只是一个人数，而变成了一个可流转的资产单位。相比之下，多数创作者平台的分配是按内容表现动态计算，规则复杂且不可预期；这里用等分换掉了全部计算，也换掉了全部争议。

第五，"Don't send a CV. Send a Signal." 与整套逻辑自洽。 准入不看履历、看作品信号；内容筛选不看热度、看同侪的公开附议与反驳；分配不看流量、看席位。产品从头到尾在拒绝同一件东西：用可量化的代理指标替代直接判断。

第六，与第一期花卷的「播客集邮册」形成一组有意思的对照。 两者都在用编号/席位制造稀缺感与可引用性，但花卷是 NO.001–012 的静态编号，1K 是可轮换的动态席位。稀缺性从「内容」移到了「发布权」——这比给内容编号更难维持，因为它牵涉真实的利益分配。

可迁移的方法

  1. 用规模上限替代排序算法，让「全看」在容量上成立。
  2. 把筛选权交给有声誉成本的人，信号质量高于匿名点赞。
  3. 策展层与讨论层分开，避免评论区与内容争夺注意力。
  4. 让收益绑定可流转的席位，而不是绑定固定的人。
  5. 准入标准用作品信号替代履历筛选。

边界与提醒

产品仍在开发中，页面正文与轮换规则的具体实现未能完整核实，多数机制目前是设计方案而非已运行的制度。1000 人默认全关注，若发布频率上升，信息量会迅速超出可读范围——规模上限必须配合发布频率上限才成立。具名附议与反驳虽然提高了信号质量，也容易产生派系、从众与对异议的抑制。收入千等分的财务可持续性、税务处理与跨平台结算规则未公开。无推荐算法意味着没有新内容发现机制，读者只能看这 1000 人，长期可能形成封闭圈层。页面已有 holder 示例，但占位数据不等于已上线。

16 CC：Occupy SaaS 与「洁净室复刻」

相关链接主页 · xlrocket.blogOccupy SaaS

身份：xlrocket.blog，第一期分享「本地优先与个人工具」，主张数据的主权在文件、不在服务。 分享对象：Occupy SaaS——发起者是被裁员的开发者，用 AI 做洁净室复刻，把商业 SaaS 重写成免费、可自部署的开源版本，并要求功能上能直接替换原产品。已完成对标 Auth0 的 ZeroAuthy 和对标 Salesforce 的 SalesCompel。现场的主要疑问是：这些复刻版由谁长期维护？ 关键词：clean-room、drop-in replacement、退出成本、治理缺位、快照漂移。

他讲了什么（含核查结果）

汇总页记两个项目的 star 数为 333 / 287。2026-11-09 核查时发现三处数字并不一致：项目主站静态页写 313 / 270，GitHub 组织页显示 399 / 349。这类差异通常来自记录时刻、静态快照与实时页面之间的时间差，本文按汇总页记录，同时保留差异。

更重要的是两处与「可直接替换」有关的核查发现：

  • 仓库 README 明确承认尚未达成 1:1 功能对齐，并列出差距；这与组织页偏乐观的描述存在张力。
  • 两个项目的 CLEAN_ROOM.md 执行标准并不一致：ZeroAuthy 写有人员防火墙（规格组与实现组分离），SalesCompel 实际采用的是 Black-Box Testing Policy，并说明不需要人员分离。同样是「洁净室复刻」，两处流程证据的强度不同。
  • 组织页与仓库中未见具名维护者、长期维护承诺或治理文档——现场那个「谁来维护」的疑问，核查后反而更尖锐。

关键点拆解

第一，「洁净室复刻」是法律概念，不是开发方法。 标准做法是两组人隔离：一组只看公开行为、写出规格文档，另一组只依据规格文档实现，全程留证据链，以证明没有复制源代码。传统软件业里这套流程成本极高——要两套人马、要文档、要审计。AI 真正改变的不是代码产量，而是「第二组人」的成本结构：让规格到实现这一步变得足够便宜，洁净室才从大公司的法务工具变成小团队可尝试的工程选项。

第二，但「洁净室」不是一句声明，是要逐项目核验的流程证据。 两个仓库的 CLEAN_ROOM.md 标准不同，恰好说明这一点：一个有人员防火墙，一个用黑盒测试且明确不需人员分离。对外部观察者来说，看到「clean-room」四个字不能推导出法律安全性，必须去看具体流程文档。

第三，「功能上能直接替换」是最难的一句，也最该被诚实对待。 drop-in replacement 意味着 API 兼容、数据格式兼容、错误码与边缘行为兼容，而不只是界面相似。README 主动承认未达成 1:1，这种把目标与现状分开写的做法，比组织页的宣传语更值得信任——第一期为 Ego Lite 厂商自测数字定下的原则在这里同样适用：给出差距与口径，主张才有意义。

第四，star 数三处不一致，是活动汇总类文档的一个结构性提醒。 现场口述、汇总页记录、静态快照、实时页面，四者的观测时间不同，任何「333 星」这样的数字都只在某个瞬间成立。本文的做法是：按汇总页记录，同时把差异写出来，不把任何一个数字当成结论。

第五，「谁来长期维护」是这类项目真正的死穴。 洁净室复刻的难点从来不是首版，而是跟随成本：Auth0 与 Salesforce 每年都在改 API、加功能、调安全策略。一个没有具名维护者、没有治理文档、没有长期承诺的复刻版，兼容性能维持多久？「可替换」这个承诺最脆弱的地方，恰恰在它宣布之后的第二年。

第六，与第一期 CC 的主张是同一条线索的推进。 第一期讲「数据的主权在文件，不在服务」，关心的是我的数据能不能带走；第二期关心我用的软件能不能被替换。两者都属于第一期文档里那句判断——「你选的不是软件，是一份长期的迁移合约」。Occupy SaaS 想夺回的，正是这份合约的主动权。

第七，同一期的线上分享里，CC 还推荐了 PhotoCraft：用 Rust 洁净室复刻 Photoshop 的开源离线图片编辑器，支持图层、蒙版、调整图层、文字与画笔，处于早期 alpha；公开说明中提到 134/135 个 PSD 样本可逐字节往返一致。同一个人当场引入两个洁净室项目，说明这不是随手分享，而是他在持续跟踪一条正在成形的技术路线：洁净室复刻 + AI。

可迁移的方法

  1. 复刻类产品先写规格、再写实现，并保留可审计的流程证据。
  2. 把「1:1 可替换」当作目标而非现状，公开列出差距清单。
  3. 引用动态数字时记录观测时间与来源页面，主动标注快照漂移。
  4. 开源之前先回答治理问题：谁维护、如何跟随上游、怎样交接。
  5. 评估工具时看退出成本，而不只是功能清单。

边界与提醒

洁净室流程的法律效力取决于司法辖区与证据完整度；「由 AI 完成实现」能否满足「独立实现」的举证要求，目前没有公开法律意见支持。复刻商业 SaaS 的 API 设计、术语与界面可能涉及商标、专利、服务条款与数据库权利，功能兼容不等于法律安全，仓库中的法律 FAQ 属项目方自述而非法律意见。「免费、可自部署」把运维责任转给用户，而认证合规、SLA、安全更新、企业级支持这些商业 SaaS 的核心价值，复刻版未必覆盖。无具名维护者与长期承诺，跟随上游迭代的能力存疑。star 数在各页面差异明显且持续增长，不宜作为质量或活跃度指标。

19 杨云童：Transparent，一层不拦截点击的翻译

相关链接主页 · yytyyf.comBob

身份：yytyyf.com，第一期的 yytyyf（OpenTrends / KeyKeeper / 多产品工作流）。 分享对象：桌面翻译工具 Transparent，以及现场被推荐的 Bob。 关键词：不抢焦点、透明覆盖层、本地模型、滚动同步、工具链分层。

他讲了什么

Transparent 是一层可拖动的透明窗口，翻译其下方任意应用的内容，不拦截点击和输入，滚动时同步更新译文。默认调用 macOS 自带的本地翻译模型，不需要联网，代价是译文质量；之后将支持接入自选的大模型。现场演示时，滚动翻译仍有延迟。

另有参与者推荐 Mac 划词翻译工具 Bob：菜单栏常驻，支持划词（默认 ⌥D）、截图（⌥S）、输入翻译（⌥A）与 PopClip，最多同时开启 10 个翻译服务、支持 30 多种服务（Apple、火山、腾讯、阿里、百度、有道、Google、Microsoft、DeepL、OpenAI 等），OCR 支持 macOS 11+ 离线识别、连续识别与二维码。其官网未列定价、开源仓库或许可证，第三方说法互相矛盾，此处不采信。

核查说明：yytyyf.com 的作品集以「把每个作业，都做成作品」为标语，Transparent 被标为 macOS 2026 已上线；独立域名 transparent.vision 目前仅有一句宣传语，功能细节以汇总页记录为准。

关键点拆解

第一，「不拦截点击和输入」是整套设计的支点。 传统翻译工具要么复制粘贴、要么划词弹窗、要么截图，都要求用户改变操作；透明覆盖层把翻译变成一层不改变原有交互的视觉信息。这与第一期 Edward Luo 把 Agent 状态放进刘海属于同一类思路：找一个常驻、不抢焦点、不劫持注意力的界面位置。

第二，「翻译其下方任意应用」意味着它处理的是屏幕内容，而不是应用数据。 好处是天然跨应用、不需要各 App 适配；代价是必须做取词/坐标对齐，滚动同步正是这个难点的外化。现场演示仍有延迟，说明这一层尚未打磨完——这个延迟不是待修的小 bug，是架构选择的价格，与本期 Transparent 用本地模型换质量是同一类取舍。

第三，默认走 macOS 本地翻译模型，与第 06 章 Owen 的 RSS 流程是同一个判断。 离线、零成本、零隐私外泄，代价是质量；但只要译文服务于 triage（看懂大意、决定要不要深究），质量换离线就划算。先确定译文在服务哪一步决策，再决定值不值得上大模型——这个顺序比「默认接最强模型」专业得多。

第四，「之后支持接入自选大模型」把质量档位交给用户，而不是替用户默认联网。 这与第一期 AllDay「本地能力买断 + 云端智能自带 Key」的定价结构同构，也延续了杨云童第一期 KeyKeeper 的核心思路：把密钥与选择权留在用户这一侧。两期之间，从「密钥治理」到「模型选择」，是同一条原则在不同层的落地。

第五，与第一期本人的对照能看出收窄。 第一期是 OpenTrends（信息聚合）+ KeyKeeper（密钥治理）+ 多产品工作流，是一套系统；第二期是一个极窄的单点工具。但关注点没变——在不打断用户的前提下把能力递过去。

第六，Bob 与 Transparent 是分层而非竞争。 划词/截图/OCR 是点状查询，透明覆盖是持续在场；粒度不同、触发方式不同，可以同处一条工具链。

可迁移的方法

  1. 设计辅助层时先问「会不会抢走用户原本的操作」，能不拦截就不拦截。
  2. 用透明覆盖换跨应用通用性，但把坐标对齐与滚动同步当作一等工程问题。
  3. 译文只用于粗读时用本地模型，把质量与联网的选择权交给用户。
  4. 现场演示暴露的延迟要如实记录，它是架构代价而非小瑕疵。

边界与提醒

屏幕取词与 OCR 依赖系统辅助功能、屏幕录制等权限，macOS 版本与权限策略变化会影响可用性。滚动同步延迟、动态内容、视频内嵌文字与复杂排版都会降低译文准确性。本地翻译模型在专业术语、长句与否定结构上质量有限；一旦接入自选大模型，屏幕内容就会离开本机，隐私模型随之改变，需要重新告知用户。作品集页标注已上线，但独立域名仅有宣传语，公开可核实的功能细节有限。涉及版权内容的屏幕翻译与展示，使用场景需自行判断。

说明：该网页与对应源码在核查时未取得可核实的功能说明，以下机制以汇总页记录为准。

他讲了什么

EmojiFuse 调用大模型的文生图接口，把 2 到 6 个 emoji 融合成一张图，可以切换风格。思路来自 Google 的 Emoji Kitchen；为了稳定输出，提示词固定了主角、环境和手势等规则。网页版在国内需要代理才能访问，安卓版可用，iOS 版尚未完成。

关键点拆解

第一，与 Emoji Kitchen 的差别是「查表」变成「生成」。 Google 的做法是预设组合——每对 emoji 有设计好的合成图，本质是有限集合；用文生图模型则是开放组合，任意 2–6 个都能出图。能力空间变大了，一致性却变差了，这才解释了为什么必须固定主角、环境、手势等规则。自由度增加多少，就要用结构收回多少。

第二，固定提示词模块是本期「模块化」母题的又一实例。 第 21 章司马光砸缸固定风格/质感/技法/配色/人物/场景，只替换「故事内容」；这里固定主角/环境/手势，只替换 emoji 输入。两者都在做同一件事：把变量收窄到一个槽位，让模型的自由度只作用于该变的地方。这是生成类产品稳定输出最有效、也最容易被忽略的手段。

第三，「2 到 6 个」是一个经过选择的输入上限。 少于 2 个无所谓融合，多于 6 个模型容易丢主体、把元素堆成一团。第一期为「硬约束降低门槛」举过 2 秒、一句话的例子，这里的 2–6 属于同类参数选择——上限不是能力不足，是对输出质量的保护。

第四，「可切换风格」把风格做成独立维度，与内容解耦。 这与第 08 章把字体拆成五维、第 11 章把课标拆成节点与边，本质上都是先把维度分开，再让用户组合。维度解耦之后，每个维度都能单独迭代，而不必重做整条提示词。

第五，这类小工具真正的产品化风险在单位成本。 每次调用都是一次文生图推理，免费开放容易被刷；风格切换又意味着同一组合会被反复生成。汇总页未提定价与限流，这是从 Demo 走向可用服务时必须补的一环。【推断】

第六，安卓可用、iOS 未完成、网页需代理，是一份典型个人项目的交付梯度。 它诚实地说明了项目离「随手可用」还有距离，与第 18 章雨杭只用 TestFlight 内测属于同一种范围控制。

可迁移的方法

  1. 生成类产品把变量收窄到一个槽位，其余全部固定。
  2. 用「固定模块 + 一个输入」的提示词结构换稳定输出。
  3. 给输入数量设上限，超过上限模型会丢主体。
  4. 让风格成为独立可调维度，与内容解耦。
  5. 按调用计费的工具，上线前先定限流与成本上限。

边界与提醒

网页与源码在核查时未能取得可核实说明，功能与机制均按汇总页转述。依赖第三方文生图接口，输出风格、可用性、价格与安全策略受上游控制。网页版在国内需代理、iOS 未完成，可触达用户范围有限。不同平台的 emoji 字形有差异，跨平台输入可能导致理解偏差；「融合」结果也难以保证符合预期。生成内容的版权与商用边界不明确。

身份：okjk.co/f9FyNU，smg.fm（自己写的在线记事本）。 分享对象：一份为《资治通鉴》主题付费课程做配图的提示词。 关键词：提示词即规格、单变量原则、官方指南、可交接流程、系列一致性。

核查说明：smg.fm 可访问，是一个在线记事本；/1105 条目未取得公开可读内容（可能需要分享密码）。因此提示词全文、六个模块的具体措辞与示例均无法核实，以下分析以汇总页记录为准。

他讲了什么

这份提示词迭代了 100 多轮，耗时近一个月，由风格、质感、技法、配色、人物、场景等固定模块组成，每次只替换「故事内容」。作者的经验是先读对应模型官方的提示词指南；按这个方法，出图成功率超过九成，非设计人员也能直接使用。

关键点拆解

第一，「100 多轮、近一个月」这个投入本身就是结论。 提示词在这里不是随手写的句子，而是被反复测试过的规格说明——更接近代码或设计系统，而不是话术。这也是本期「把隐性判断显性化」最直观的例子：把「画得好看」拆成六个可写、可改、可复用的模块。

第二，「每次只替换故事内容」是单变量原则。 固定风格、质感、技法、配色、人物、场景，只让内容变化，于是风格一致性由结构保证，而不是靠模型自觉。系列化配图最大的敌人是风格漂移，单变量结构是对它最直接的解法。这与第 20 章固定主角/环境/手势、第 08 章用参照锚点校准量表，是同一套控制变量的方法，只是应用对象不同。

第三，「先读对应模型官方的提示词指南」最容易被跳过，也最值钱。 不同图像模型对描述顺序、权重语法、否定词与长句的响应差异很大，把 A 模型的经验照搬到 B 模型常常失效。这条经验与第 05 章 Sean Shao 的提示词恰好构成对照：一个靠官方指南做校准，一个用架构故事作解释——前者可迁移，后者不可。

第四，「非设计人员也能直接使用」说明产物不是一张图，而是一条可交接的生产流程。 判断被写进了模块里，执行者不必再具备审美判断力。这与第 03 章 Hao 把咨询经验拆成 skill 完全同构：把专家的隐性能力转成别人可执行的步骤，是 AI 时代最实在的一种知识工程。

第五，「成功率超过九成」要按自述数据读。 分母、判定标准、所用模型与失败案例均未公开；结合「100 多轮迭代」看，它更像是对一套已收敛流程的经验值，而不是模型能力指标。第一期处理 Ego Lite 自测数据时的原则在这里同样适用。

第六，把本期这些「结构化」案例并排看，会看出这一期真正的主角。 字体五维量表、课标的 1083 节点与 2071 条边、GEO 的 llms.txt、Brand Logo Finder 的 QC 清单、Comma 的 Task 与 Needs Review、这里的六模块提示词——它们分属完全不同的领域，但做的是同一个动作：把原本只存在于人脑里的经验，写成机器可执行、他人可复用、自己可检查的结构。

可迁移的方法

  1. 把系列化输出拆成固定模块 + 单一变量，用结构保证一致性。
  2. 换模型前先读该模型官方的提示词指南，别照搬旧经验。
  3. 把提示词当作可版本化、可交接的规格文档维护。
  4. 用「非专业者能否直接使用」检验经验是否真的被结构化了。
  5. 记录迭代轮数与失败案例，它们往往比最终提示词更有价值。

边界与提醒

/1105 条目未能公开读取，提示词全文、模块措辞与示例无法核实；「100 多轮、近一个月、成功率超九成」为分享者自述，无分母、判定标准与模型信息。模块化会牺牲灵活性，题材跨度大时固定的人物与场景模块可能反而不适用。提示词效果高度绑定特定模型版本，模型更新后需重新校准——这既是「先读官方指南」要反复做的原因，也是这类资产的主要维护成本。为付费课程生成的配图涉及商业使用，需确认模型服务条款、素材版权与历史题材的表现边界。

第五部分 · 横向总结：21 个案例收敛出的 5 条判断

第一期收敛出的核心判断是「真正的瓶颈已经从执行转移到判断」。第二期没有推翻它，而是往下走了一层：这批人不再争论判断重不重要，而在动手把判断写成机器可执行、他人可复用、自己可检查的结构。五条判断由此展开。

判断一：组织单位正在从「会话 / 产品」变成「任务 / skill / MCP」

这一期至少八处出现了同一种形态：

  • Comma 的官方定义是 "sessionless"、"built around Tasks, not chats"，架构为 Router 承接、Worker 执行，决策项停在 Needs Review 看板；
  • 海涛同时贴出的 DeepSeek Harness 文章独立给出同一套双层架构，并点明「Session 应当是系统的实现细节，而不应是用户的认知负担」「多任务的上限取决于人的注意力」；
  • Hao 把咨询经验拆成可版本化的 skill，SpringBrand 用 MCP 分发能力，monid.ai 用一个 skill 接入数千工具，Ego Lite 配 ego browser 技能把无 API 的 SaaS 变成 CLI，social-auto-upload 附带供 Agent 调用的 Skill，PostPiper 通过 MCP 在 Agent 里起草与排期。

两层变化要分开看。能力的粒度变细了：接口从「给人用的界面」变成「给 Agent 用的能力描述」，集成成本从 N×M 压成 N+M。工作的单位也变了：从会话变成任务，不是因为任务更先进，而是因为并行之后 bottleneck 落在人的注意带上——一个人只能同时跟进 3–5 个活跃会话，于是「把决策攒成队列」比「让 Agent 随时打断你」更合理。

对照第一期：第 4 条「护城河是细节密度」讲的是产品竞争力的来源；这一条讲的是产品以什么形态存在。当能力可以被一份文本描述完整交付时，「产品」这个单位的边界本身开始松动。

判断二：筛选权回流个人，同时「被 AI 选中」成为新战场

这两件事看起来相反，实际是同一场变化的两面。

  • 收回筛选权：Owen 把摘要与译文前移到 RSS 列表层、ZotWatch 在私有空间跑两级筛选、custombili 让用户自己写规则、HackerTube 用「被反复推荐」作信号、BestBlogs.dev 用「AI 初评 + 人工精审」——本期共五个案例，几乎都把人放在筛选链路的最后一环。
  • 争取被选中：绘页的 robots.txt 与 llms.txt、0xinhua 从 Network 面板拆出模型真实搜索词、司马光砸缸的模块化提示词、SpringBrand 的四级证据标签。

当推荐系统的调用方从人变成 Agent，「我要看什么」与「我要被看见」就合并成了一个问题：都是在给机器准备一份可读、可切分、可引用的结构。llms.txt 里写的「用途、人群、定价、与竞品区别」，和 0xinhua 观察到的「更新时间、准确数字、对比表格、页首摘要」，本质是同一类东西——可被直接引用的事实卡。

对照第一期：第 2 条说「可编辑比能生成难，也比能生成值钱」；第二期的版本是「可被机器正确读取，比被人看见更前置」。第一期第 18 位 imxiaorong 讨论「训练一条只属于自己的信息流」时，对手还是平台算法；这一期，对手变成了替人跑腿的 Agent。

AI 能放大的从来不是模糊的经验，而是已经被写成结构的东西。 80%→95% 的提升来自把步骤写清楚，不是换了更强的模型；「非设计人员也能直接使用」说明判断已经被搬进了模块里；「成功率超九成」是 100 多轮迭代收敛出的流程，不是一句提示词的魔力。

对照第一期：第 5 条说瓶颈从执行转移到判断；这一期补上了后半句——判断只有被写成可测、可复用、可检查的形式，才真的能起作用。「知道什么值得做」是人的事，「把什么值得做定义成机器能执行的形式」，是这一期这批人真正在做的事。

判断四：把最终决定权留在人这一侧

不是一句价值观，而是一组可指认的架构选择：

  • 数据留在本地：Transparent 默认 macOS 本地翻译模型、《孩子要学的一切》进度只存本地、Occupy SaaS 可自部署、ZotWatch 在私有 GitHub 空间计算、Comma 可自托管；
  • 闸门由规则触发：Comma 的 Needs Review、Brand Logo Finder 的「缺失/失败/存疑/未复核一律阻断 QC」、医桥中国「人工复核后才发客户」、AI 助手主动声明 "not a doctor"；
  • 主动设限：1K 只有 1000 席位且没有推荐算法、ZotWatch 每天最多 30 篇且「不为了凑数量降低要求」、《孩子要学的一切》不设打卡积分排行榜推送、Gesture Synth 把和弦限制在调内。

关键在闸门的位置与触发方式：不是靠人主动巡检，而是由置信度、规则或容量自动把事项推到人面前。主动放弃一部分能力，换来的是可预测性——1K 没有算法，是因为 1000 人全量关注让算法不必存在；课标图谱不打卡，是因为地图的价值在「需要时查得准」。

对照第一期：第 3 条「合规与授权正在成为技术方案的一部分」在这里被扩展成「控制权」——不只是找到官方允许的路径（如第一期微信读书 Skill API Key），还要把最终决定权写进架构。第二期的 Occupy SaaS 与 PhotoCraft 则把这条推到了更激进的位置：干脆自己重写一个可替换的版本。

判断五：门槛没有消失，只是移动了位置

本期有一批「没有背景的人做成了原本做不了的事」：雨杭与合作者没开发过 tvOS，代码与部署全交给 AI；Peter Lei 没有算法背景，在 MacBook 上让 Agent 自主研究两天；小禾用 AI 半小时搭好服务网站；司马光砸缸的提示词让非设计人员也能出图；Cassie 换掉笔记与选择题，改用生成视频才把算法学下去。

但把这几例与判断三并排看，就会发现跨过去的从来只是实现门槛，评估门槛原封不动地留在原地：

  • Peter Lei 能跑通实验，但「benchmark 选得对不对」「是否过拟合验证集」仍需领域判断；
  • 雨杭能写出客户端，但「哪些是平台限制、哪些是模型写错」无人能分辨，长期维护存疑；
  • 小禾能半小时建站，但业务能否成立取决于线下履约，而个人站自标 "Prototype / User Validation"；
  • JJ Ying 的五维量表要可用，必须靠参照锚点校准、靠固化打分结果防漂移；
  • 奚圣波能把 llms.txt 写全，却仍只能说「见效时间难以预测」。

外行能跨过实现门槛，跨不过评估门槛。 这也是为什么本期反复出现 benchmark、参照分数、证据分级、来源绑定、人工复核、可观测日志这些「看起来不产出功能」的东西——它们正是被移动后的新门槛。

对照第一期：第 5 条的原文是「当生产成本塌陷，稀缺性转移到选择、品味与验证上」。第二期给出的证据更具体：稀缺的不是「有判断力」这个抽象品质，而是「把判断力写成可验证结构」的工程能力。
